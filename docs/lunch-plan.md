# 점심 메뉴 추첨: 프로토타입부터 완성품까지

작성일: 2026-11-13 · 작업 브랜치: `codex/lunch-prototype`

## 목표와 기본 흐름

음식점 후보를 준비하고, 룰렛 등으로 점심 식사 장소를 정한다. 이후 직원들이 참가 링크로 같은 추첨식을 시청하고 대화할 수 있도록 확장한다.

`후보 목록 준비 → 포함·제외 설정 → 후보 확정 → 난수로 결과 결정 → 추첨식 재생 → 결과 확인`

- 기존 React/TanStack Start/Cloudflare Workers와 요청별 난수 엔진을 사용한다.
- 샘플·직접 입력·엑셀·검색 결과는 같은 후보 모델로 변환한다.
- 추첨은 후보의 고유 ID를 기준으로 하고, 애니메이션은 확정된 결과를 공개한다.
- 먼저 룰렛을 만들고, 사다리·오리 경주·핀볼은 별도 연출 모듈로 추가한다.
- 이번 착수 범위는 1단계다. 이후 단계는 앞 단계의 실제 사용 결과를 보고 작은 단위로 진행한다.

예상 일정은 프로토타입 확인 후 단계별로 산정한다. 공동 시청과 외부 검색을 한 번에 묶어 검증하지 않는다.

## 1단계: 이번에 구현할 프로토타입

- 주소: `/lunch`. 기존 번호 생성기 상단에서 진입한다.
- 사용자가 제공한 `선정릉_점심식당_목록.xlsx`의 `식당 목록!A5:D39` 35행을 정적 후보 데이터로 사용한다. 원본 파일은 수정하지 않는다.
- 음식점 이름·분류·회사 기준 거리와 순서를 그대로 보존한다. 편의점·카페도 임의로 빼지 않고 사용자가 포함·제외한다.
- 8개 분류는 한식 12곳, 편의점 8곳, 카페/베이커리/패스트푸드 7곳, 샐러드·일식·분식 각 2곳, 편의점/마트·중식 각 1곳이다.
- 거리는 제공 파일의 회사 기준 값(67~420m)이며 현재 기기 위치로 계산한 실시간 거리가 아님을 표시한다. 메뉴·평점·영업 여부는 원본에 없어 임의로 채우지 않는다.
- 분류별로 후보를 고르고 각 음식점을 포함·제외할 수 있다.
- 기존 `generateRandomNumbers`로 후보 인덱스 1개를 요청한다. 실패하면 오류와 재시도를 제공하며 임의의 다른 결과로 바꾸지 않는다.
- 요청을 시작할 때 후보 목록을 복사해 고정한다. 요청·회전 중에는 후보 변경과 재시작을 막는다.
- 모든 후보는 같은 크기의 룰렛 칸을 갖는다. 선택한 칸의 중앙이 고정 바늘에 정확히 멈춘다.
- 후보가 많을 때는 칸에 번호를 표시하고 후보 목록에도 같은 번호를 표시한다. 전체 이름은 후보 목록과 결과에서 확인한다. 칸을 줄이려고 일부 후보를 자동으로 제외하지 않는다.
- 룰렛과 결과는 같은 스냅샷을 사용한다. 결과에는 음식점·메뉴·원래 생성 시각·실제로 사용한 난수 출처를 표시한다.
- 감소 모션에서는 회전 없이 같은 결과를 보여준다. 결과는 텍스트로도 제공하고 키보드로 모든 기능을 사용할 수 있게 한다.
- 방·채팅·위치 검색·커스텀 입력·엑셀의 작동하지 않는 버튼은 노출하지 않는다.
- V0에는 외부 API 연동 키나 새 라이브러리가 필요하지 않다. 난수 취득 경로만 기존 시스템을 사용한다.

## 공통 데이터와 목록 관리

초기 후보 모델은 `id, name, category`와 선택적인 `menu, distanceMeters`다. 대표 메뉴가 없는 원본에는 메뉴를 만들어 넣지 않는다. 후속 단계에서 아래 필드를 추가할 수 있다.

- 출처: `sample | custom | excel | naver | other`
- 외부 제공자 ID, 주소, 위도·경도, 원본 링크, 조회 시각
- 사용자가 적는 메모와 포함 여부

분류·제외 상태는 후보 데이터와 분리한다. 같은 이름의 음식점도 주소나 메뉴가 다를 수 있으므로 이름만으로 자동 병합하지 않는다. 룰렛 칸 순서와 고유 ID를 회차 스냅샷에 함께 저장한다.

### 엑셀 왕복 편집

기본 열은 `id / 음식점명 / 대표메뉴 / 분류 / 주소 / 메모 / 포함여부`로 잡는다. 처음 만드는 목록에서는 ID를 비워도 새 ID를 생성한다.

1. 현재 목록을 실제 `.xlsx` 파일로 내려받는다. CSV를 `.xlsx`로 이름만 바꾸지 않는다.
2. Excel에서 행을 추가·수정·삭제한다.
3. 업로드하면 원본을 바꾸지 않고 새 목록을 검증·미리보기한다.
4. 추가·수정·삭제될 수와 오류 행을 확인한다.
5. 사용자가 적용하면 목록 전체를 원자적으로 교체하고 이전 버전을 복구할 수 있게 한다.

업로드 크기·행 수·열 길이를 제한하고 수식은 실행하지 않는다. 추첨 중인 방의 고정 목록은 편집으로 바뀌지 않으며 다음 회차부터 적용한다. 파서 라이브러리는 2단계 착수 시 유지보수·라이선스·보안 상태와 번들 크기를 확인해 선택한다.

## 공동 시청: WebSocket + Durable Object

현재 Cloudflare 환경에서 방마다 Durable Object 하나가 상태를 소유하고 WebSocket으로 참가자에게 전달하는 구성을 권장한다. 공식 문서가 채팅·멀티플레이 세션의 조정 용도로 소개하는 구조다.

참고: [Cloudflare WebSocket 문서](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)

### 방의 상태

`대기 → 후보 잠금·추첨 요청 → 카운트다운 → 연출 재생 → 결과 공개 → 다음 회차`

- 초대 링크는 손님 입장 권한만 제공한다. 방장 권한은 별도 토큰으로 서버에서 확인한다.
- 방장이 시작하면 서버가 회차 ID·후보 버전을 고정하고 기존 난수 엔진을 한 번 호출한다.
- 난수 요청 중 중복 시작은 거부하고 실패하면 대기 상태로 복구한다.
- 서버는 `drawId, listVersion, candidateIds, winnerId, startedAt, duration, animationVersion, animationSeed` 등을 회차에 저장한다.
- 회차에는 후보의 이름·메뉴·분류까지 포함한 불변 스냅샷을 보관한다. ID만 저장한다면 반드시 해당 목록 버전을 불변 상태로 다시 조회할 수 있어야 한다. 다음 회차의 수정으로 이전 결과 문구가 바뀌지 않아야 한다.
- 시작각·목표각과 공통 easing도 회차에 고정한다. 재접속자의 로컬 누적 회전각을 사용하지 않는다. 1단계의 누적각 헬퍼는 단독 사용용이며, 공동 시청에서는 서버가 정한 회차별 각도와 경과 시간으로 화면을 복원한다.
- 서버가 정한 시작 시각을 공유하고 클라이언트는 서버 시간과의 오차를 보정해 경과 시간 기준으로 재생한다. 각 기기에서 별도로 재추첨하지 않는다.
- 게임 영상을 송출하는 방식이 아니다. 후보·결과·타이밍을 전달하고 각 브라우저가 같은 연출을 재생한다.
- 프레임 단위의 완전한 동시성은 네트워크·기기 차이로 보장하지 않는다. 같은 회차·결과와 일관된 진행 시점을 목표로 한다.
- 뒤늦게 입장하거나 재접속하면 저장된 스냅샷을 받아 진행 중간부터 재생하거나 완료 결과를 보여준다.
- 후보를 미리 확정하는 연출은 보안상 결과를 비밀로 숨기는 기능과 별개다. 비공개 결과가 꼭 필요해지면 공개 시점 프로토콜을 별도로 설계한다.

### 채팅과 운영

닉네임과 텍스트 채팅으로 시작한다. 메시지 길이·전송 간격·최근 보관 개수를 제한하고 HTML을 실행하지 않는다. 초안은 로그인 없이 짧게 유지되는 회사 점심방이며, 만료 시간·참가 인원·채팅 보관 정책은 3단계 전에 확정한다. 방 종료와 유휴 정리도 서버가 처리한다.

방 상태는 저장소에 남겨 Durable Object의 휴면·재시작 후에도 복구한다. 연결별 닉네임·권한은 연결 attachment 등으로 복원한다. 호스팅 요금·쿼터와 설정 변경은 3단계 구현 전에 공식 가격·제한 문서로 다시 확인한다.

## 네이버 연동 조사 결과

2026-11-13 공식 문서 기준 네이버 지역 검색 API는 업체·기관 검색을 제공한다.

- 검색어 기반이고 `display` 최댓값은 5, `start` 최댓값은 1이다.
- 문서의 요청 파라미터에는 위도·경도 중심점이나 반경이 없다.
- `sort=random`의 의미는 **정확도순**이다. 무작위 음식점 추첨 옵션으로 사용하지 않는다.
- 따라서 API 하나로 ‘내 위치 주변의 모든 음식점’을 얻는다고 약속할 수 없다.

참고: [네이버 지역 검색 공식 문서](https://developers.naver.com/docs/serviceapi/search/local/local.md)

4단계에서 확인할 사항:

1. ‘역삼동 점심’, ‘역삼동 한식’ 같은 지역·분류 검색으로 필요한 후보 수와 품질을 확보할 수 있는지 실측한다.
2. 결과를 합칠 경우 업체 중복을 정리하고, 검색 결과에서 사용자가 추첨 후보를 고르게 한다.
3. API의 좌표 형식·주소·원본 링크를 정규화한다. 직선거리와 실제 도보거리를 혼동하지 않는다.
4. 결과 저장·재표시·출처 표기의 허용 범위를 약관에서 확인하고 적용한다.
5. 정확한 좌표·반경 음식점 검색이 필수라면 다른 공식 장소 검색 API와 함께 비교한다. 카카오 로컬 API는 비교 후보이며, 이번 프로토타입에서 제공자를 변경하거나 키를 요청하지 않는다.

참고: [카카오 로컬 공식 문서](https://developers.kakao.com/docs/ko/local/dev-guide)

위치 권한은 검색 기능을 사용자가 선택했을 때 요청하고, 주소 직접 입력 경로도 제공한다. API 키는 서버에서만 사용한다.

## 게임 연출 선택

- 룰렛: 기존 React + SVG/CSS로 구현한다.
- 사다리: 매칭 결과와 표시 경로가 일치하도록 별도 경로 모델을 검증한다.
- 오리 경주·핀볼: 필요해질 때 Phaser를 해당 화면에서만 불러온다. 핀볼 충돌 연출에는 Matter Physics를 검토한다.
- 게임 엔진을 서버에서 렌더링하지 않는다. 입력·방 관리·결과 기록은 기존 웹앱이 맡는다.
- 모든 연출에는 회전·이동을 줄이는 설정과 텍스트 결과를 제공한다.

## 매 단계의 검증

- 후보가 0~1개일 때, 제외 목록·분류 변경, 긴 이름, 네트워크 실패, 잘못된 응답, 중복 실행을 확인한다.
- 선택 후보와 결과의 일치, 룰렛 바늘 정렬, 재실행 회전 방향을 테스트한다.
- 키보드·모바일320px·감소 모션 경로를 확인한다.
- 공동 시청 단계는 두 브라우저, 늦은 참가, 재접속, 방장 이탈, 중복 시작·오래된 회차 메시지를 확인한다.

### 후속 화면 개선 — 2026-11-13

- 화면 높이에 맞춰 결과와 룰렛을 배치하고, 긴 후보 목록만 내부에서 스크롤하도록 바꿨다. 작은 화면은 ‘룰렛·결과’와 ‘후보’ 보기를 전환한다.
- 룰렛 중앙을 실제 키보드 접근 가능한 추첨 버튼으로 바꿨다. 결과를 상단·앞쪽에 두고, 난수 출처를 펼치면 생성 시각을 확인할 수 있다.
- 모든 분류가 처음부터 켜져 있고, 개별 분류를 독립적으로 끄고 켤 수 있다. ‘전체’는 모든 분류를 다시 켜며 개별 식당 제외 상태는 유지한다.
- 실제 브라우저의 1288×1244, 1288×720, 320×740에서 페이지 바깥 스크롤 없이 결과·중앙 버튼을 확인했다. RTL과 독일어 긴 식당명은 644×622에서 점검했다. 이 크기는 1288×1244 화면의 200% 확대에 해당하는 CSS 공간이며, 브라우저 자체의 200% 줌 조작은 별도로 검증하지 않았다.
- 전체 테스트 403개, 타입 검사, 변경 파일 검사와 배포용 빌드가 통과했다. 후보 보기에서 시작한 추첨을 좁은 화면에서도 계속 볼 수 있는 회귀 검증을 포함한다.

- 모든 칸에 원본 번호와 식당명 라벨을 표시한다. 긴 이름은 줄여 표시하고 후보 목록에서 전체 이름을 확인할 수 있다.
